## HMS-08: allocations (REQ-14–REQ-19, BR-1–BR-3)

Admin and Warden users allocate beds at `/allocations/create/`, transfer at
`/allocations/<id>/transfer/`, and release with a vacate date at
`/allocations/<id>/release/`. The existing POST-only completion action remains
compatible and supplies today's date. Student users cannot access staff routes.
The list is paginated; a student's history is available at
`/students/<student-pk>/allocations/` in descending date/ID order.

JSON clients use a session and CSRF token, `Content-Type: application/json`
for writes and `Accept: application/json` for reads. POST `/allocations/`
accepts `{student_id: <SRN>, bed_id: <integer>, allocated_on?: <ISO date>}`.
Transfer accepts `{new_bed_id: <integer>}` and release accepts
`{vacate_date: <ISO date>}`. Responses identify the allocation and bed;
conflicts return 409 and gender/eligibility violations return 422.

Transfers close the original allocation and create a new record, preserving
the old bed and dates. Allocation, transfer, release, bed updates and their
actor-specific audit events commit together. Failed writes or audit errors
roll back the whole operation. History is read-only in Django admin, and
ordinary ORM bulk writes/deletions are blocked.

Operations lock Student first, then Rooms and Beds in increasing PK order,
then Allocation. Student deactivation takes the same Student lock. Unique
active IDs and database checks prevent conflicting or forged active records
on MySQL, including inserts that bypass application validation.

Migration `allocations.0003` repairs the derived active IDs left null by
`0002` and synchronizes available beds with active records. It first validates
existing conflicts and dates. It stops for ambiguous/inconsistent records;
it never invents a historical vacate date. Correct such records using verified
business dates before retrying. Apply migrations with application writes paused.

Run `python manage.py test allocations students hostels --noinput` for focused
checks, or `python manage.py test --noinput` for all applications. Added tests
exercise transfers/history, role access, CSRF, rollback, audit failure,
database checks, upgrade/backfill behavior, competing allocation requests,
deactivation races and simultaneous transfers between rooms.

The full MySQL suite passed 110 tests after the allocation implementation.
Payment/report results are recorded below as those implementations are verified.

## HMS-09: payments (REQ-20–REQ-22, BR-5)

Admin and Warden users record payments at `/payments/create/`, search receipts
at `/payments/` and view a student's payment status from the student list.
Receipt pages offer a PDF download and a separate correction form. Both the
HTML and JSON routes require staff authorization; writes require CSRF.

POST `/payments/` accepts
`{student_id: <SRN>, amount: "5000.00", date: "2026-10-26", mode: "UPI", reference?: "TXN123"}`.
Modes are `Cash`, `UPI` and `Bank Transfer`. Amounts use at most eight integer
digits and two decimal places. Normal payments must be positive; dates cannot
be in the future. The optional reference is at most 30 letters/numbers.
The response is 201 with the receipt number and recorded fields. Receipts are
available at `/payments/<receipt_no>/receipt/` and
`/payments/<receipt_no>/receipt.pdf`; PDF contents are generated by ReportLab.
`GET /students/<student-pk>/payment-status/` returns `status`, `fee`, `paid`,
`due` and room/hostel information when requested as JSON.

Corrections POST to `/payments/<original-receipt_no>/adjust/` with `amount`,
`date`, `mode`, optional `reference` and required `adjustment_reason` (200
characters maximum). A negative amount reverses some or all of the original;
a positive amount adds to it. All corrections link directly to the original
payment for the same student, never another adjustment. Their net amount may
not make the original negative, and their date cannot predate the original.
Each receives its own receipt. Original payments and corrections are immutable
and protected from ordinary ORM bulk changes and deletion; Django admin is
read-only. The application provides no edit/delete endpoint.

Receipt numbers are `R` followed by eleven digits (12 alphanumeric characters).
`payments.0001` seeds the single receipt counter. A payment locks Student,
then its original payment if correcting, then the counter. Counter increments,
payment insertion and the actor-specific audit entry share one transaction.
Concurrent committed payments have consecutive unique numbers; rejected or
rolled-back writes consume no number. Do not reset the counter on an existing
database, and do not use bulk inserts to import payments.

Admins configure nonnegative `Room.fee_amount` through the existing room form.
`hostels.0002` adds it with a zero default to preserve existing rooms. Zero means
the fee has not been configured; status remains Pending until a positive fee
is assigned. Existing room form clients that omit the fee preserve its value.
As the SRS defines no billing period, v1 compares all the student's signed
payments with the current allocation's room fee, or the most recent completed
allocation's fee after release. Cancelled allocations do not supply a fee.
A transfer uses the new room fee; release retains the last fee. Advance
payments without an allocation are allowed and remain Pending. With a positive
assigned fee, zero paid is Pending, part paid is Partial and at least the full
fee is Paid; due never drops below zero. No recurring/semester invoices are
inferred. Fee changes affect this current-status calculation and do not alter
recorded payment amounts.

Install `requirements-dev.txt` to run the verification suite (including pypdf
receipt parsing). Runtime deployments need only `requirements.txt`.
`python manage.py test payments hostels --noinput` passed 44 tests on MySQL
8.4.9, including concurrent numbering/corrections, rollback, immutable history,
balance transitions, permissions, CSRF, validation and actual PDF contents.

## HMS-11: reports (REQ-23, TC-RPT-01)

Staff open `/reports/occupancy/` or `/reports/payment-status/` from Reports on
the navigation/dashboard. `?hostel=<hostel-pk>` filters either report; an empty
filter includes every hostel, including inactive/empty hostels, or every student
including students without an allocation. A student is assigned to the current
or most recent completed allocation's hostel for the payment report. Released
students remain visible in that hostel's payment report.

`Accept: application/json` (or `?format=json`) returns `{rows, generated_on}`.
`?format=csv` downloads the same rows and numeric values. The occupancy report
includes total, occupied, available and maintenance bed counts and percentage
occupied, safely returning 0.00% for zero beds. An active allocation takes
precedence over a stale Available/Maintenance flag. Otherwise, an Occupied flag
counts as occupied, Maintenance counts as maintenance and Available counts as
available. Historical allocation rows cannot multiply a bed count. Thus each
valid bed belongs to one count, and maintenance beds never count as available.

The payment report includes student ID/name, hostel/room, fee, paid, due and
Paid/Partial/Pending status using the policy above. Independent subqueries avoid
duplicating payment sums when a student has several allocations. Occupancy uses
two data queries irrespective of hostel count; payment status uses one query
irrespective of student count. Both reports include a generated timestamp.
CSV output uses UTF-8 with a BOM, quotes commas/newlines correctly, and prefixes
spreadsheet formula-like names with an apostrophe so they remain literal text.
HTML escapes names normally. Both reports are read-only and staff-only.

`python manage.py test reports --noinput` passed all ten current report tests, covering
calculations, history, stale flags, maintenance, empty hostels, filters, payment
corrections, HTML/JSON/CSV agreement, CSV text handling, access and query counts.

## Repeatable combined verification

With the MySQL application/test database grants described in the README and
`requirements-dev.txt` installed, run `python scripts/run_checks.py`. Do not run
two suites against the same MySQL test database at once. The runner checks
Python errors/import order with Ruff, Django/database configuration and migration
consistency, creates a separate fresh test database, runs all tests under
branch-aware coverage, enforces a 70% combined statement/branch coverage minimum,
and saves JUnit XML, logs, coverage XML/JSON and `run.json` in an ignored
timestamped `test-results/` directory.
The login/dashboard timing check is intentionally skipped under coverage and
then run separately without instrumentation. Its result is saved in
`timing-smoke.txt` and included in the runner's overall success status.
It never migrates or populates the application database. `run.json` records the
commit, dirty status, versions, test totals, coverage and each check's exit code;
it records no credentials or connection settings.

GitHub Actions runs the same command on Python 3.11 and 3.14 against MySQL 8.4
LTS, after applying migrations to a fresh application database. Each matrix job
uploads its own `hms-test-evidence-py<version>-<commit>` artifact for 30 days.
Open the corresponding PR check to download the complete evidence. This covers
automated module/integration verification; broader Sprint 2 acceptance,
browser/OS compatibility, backup/recovery drills and team sign-off remain #13.

order. Their original stacked bases were retargeted to main after each parent
merged.
